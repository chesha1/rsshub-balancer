# 上游重定向处理

入口转发普通 Feed 路由时，RSSHub 上游可能返回重定向。本文说明入口的处理规则、实现方式和设计考虑。实现位于 [upstream.ts](../packages/server-core/src/upstream.ts) 的 `fetchWithinUpstream()`。

## 处理规则

入口只在同一个上游内跟随重定向，并按跟随后的最终响应判断该上游能否处理当前请求。

| 上游响应 | 入口处理 |
| --- | --- |
| 2xx，以及 304 等不表示跳转的 3xx | 转发给客户端，记为该上游成功 |
| 301、302、303、307、308，跳转目标与该上游同源 | 在该上游内请求跳转目标，最多 3 跳，按最终响应判断 |
| 跳转目标指向其他站点，或 `Location` 缺失、无法解析 | 该上游失败 |
| 跟随超过 3 跳 | 该上游失败 |
| 4xx、5xx、连接错误、超时 | 该上游失败 |

- `Location` 可以是相对路径，按当前请求地址解析；同源指协议、主机和端口都相同。
- 跟随时沿用原请求的方法和请求头，同一个上游内的全部请求共用 15 秒超时。
- 上游失败时写入失败标记，再尝试下一个候选；全部失败时返回 502。客户端只会收到最终内容或 502，不会收到 301、302、303、307、308，订阅地址保持不变。
- 缓存探测、失败标记和指标都按原始请求路径记录；指标中的上游是最终返回响应的实例。

## 实现方式

`fetchFromUpstream()` 通过 hono 的 `proxy()` 转发请求，由它复制客户端请求头、去掉逐跳头并整理响应头。`proxy()` 没有“只跟随同源重定向”的选项，与重定向相关的只有 fetch 标准的 `redirect`，因此入口把 `fetchWithinUpstream()` 作为 `customFetch` 传入，替换 `proxy()` 内部使用的 `fetch`。

`fetchWithinUpstream()` 以 `redirect: 'manual'` 请求上游。Node 和 Workers 中 `manual` 返回真实的 3xx 响应，可以读到状态码和 `Location`；浏览器中同一取值返回读不到 `Location` 的 `opaqueredirect`，这里不涉及。遇到可以跟随的重定向时，它释放重定向响应的正文，用同样的方法、请求头和超时信号请求跳转目标；不能跟随时抛出异常，由 `fetchFromUpstream()` 的尝试循环按该上游失败处理，与连接失败、超时相同。

## 设计考虑

### 重定向只在发出它的上游内成立

客户端只知道入口地址。上游返回的 `Location` 通常是相对路径，客户端按入口地址补全，跟随时发出的是一个新的入口请求，会被重新选路。各上游运行的 RSSHub 版本不同，同一组路由在不同版本中的重定向方向可能相反，因此一个上游给出的重定向只对它自己的版本成立。

例如 RSSHub 在 2026-03-10（`8637e63`）把 `/picnob` 重定向到 `/picnob.info`，2026-06-06（`055c5b7`）又把 `/picnob.info` 重定向到 `/picnob`。2026-10-02 的候选上游同时运行这两类版本，各自的正式路由都抓取失败。若把重定向交给客户端，请求 `/picnob/user/…` 时，新版上游返回 503 被跳过，旧版上游的 301 被当作成功返回；请求 `/picnob.info/user/…` 时正好相反。选路每次都停在发出重定向的那组上游上，客户端在两个地址之间来回跳转；这些 301 带 `Cache-Control: public, max-age=300`，被 Cloudflare 缓存后，循环会稳定存在。

在同一个上游内跟随时，重定向的起点和终点属于同一个版本。上例中每个上游最终都返回 503，入口返回 502；只要有上游能返回内容，客户端就直接拿到内容。

### 成功时返回最终内容

入口直接返回跟随后的最终内容，不把确认可用的 301 交给客户端。即使两个版本各自的正式路由都能出内容，交出去的 301 仍会让下一跳被重新选路，落到另一个版本时又拿到反方向的 301，被 Cloudflare 缓存后同样会循环。

代价是客户端看不到站内重定向。有的阅读器会根据 301 更新订阅地址，经过入口时不会发生；在上游版本不一致时，这也避免了订阅地址被来回修改。

### 指向其他站点的重定向按失败处理

RSSHub 路由通过 `ctx.set('redirect', …)` 发起重定向，由中间件统一返回 301。2026-10-02 核对 RSSHub 源码，共 12 处使用，除 `weibo/timeline` 的 2 处外都是站内相对路径，用于路由别名和迁移。`weibo/timeline` 在实例的微博 token 失效时跳到微博 OAuth 授权页，供实例管理员在浏览器中授权。实例本身也可能跳到其他站点，例如前置了登录网关、迁移了域名，或域名失效后跳到停放页。这些情况都表示该上游当前给不出订阅内容。

把这类重定向交给客户端时，阅读器拿到的是用不上的页面，而换一个上游可能就能成功，例如微博 token 有效的实例；入口还会把它记为该上游成功，不写失败标记，后续请求继续选中它；301 还可能让阅读器把订阅地址永久改到外部，此后绕开入口。按失败处理后，入口会换下一个上游。

### 入口不请求其他站点

fetch 的 `redirect: 'follow'` 也会在同一个上游内跟随相对路径的重定向，同样能消除上面的循环，但它会跟随任意跳转：

- 外部页面通常返回 200。2026-10-02 直接请求微博 OAuth 授权页，返回 `200 text/html`。入口只按状态码判断成败，会把授权页、登录页或停放页当作订阅内容返回并记为成功，失败转移失去作用。
- 跳转目标由公开实例列表中的第三方运营者决定。上游返回指向 `http://127.0.0.1:…` 或云厂商元数据地址的重定向时，Origin 会请求这些内网地址，并把内容返回给请求方；上游还可以在缓存探测中返回命中，让自己被优先选中。Workers 跟随跨域跳转时还会带上客户端的全部请求头。
- 跳数上限由运行时决定，规范为 20 跳。上游内部出现循环时，一次尝试要发出二十多个请求，在 Workers 上每一跳都计入子请求数。

在 `follow` 之后检查 `res.url` 是否还在原上游，只能避免第一点，因为外部请求已经发出。`redirect: 'error'` 则把所有重定向都当作失败：所有上游都用 301 迁移某个路由时，内容就在下一跳，入口却返回 502，还会给健康的上游写失败标记。

### 跳数上限

RSSHub 迁移路由通常只有一跳，上限 3 只用于截断异常的跳转链。上游内部出现循环时，最多发出 4 个请求就判定该上游失败，此后 6 小时内同一路径会跳过它。

## 已知限制

- 跳转目标只在发出重定向的上游内请求，不会交给其他上游。如果较新版本删除了旧路由、对旧路径返回 404，而保留重定向的旧版本抓取失败，即使较新版本能处理新路径，入口也会返回 502。RSSHub 迁移路由时会保留只做重定向的旧路由（如 `picnob.info`），目前不处理这种情况；若出现，可以在所有上游都失败、且有上游给出过站内跳转目标时，再用其他上游请求该目标。
- RSSHub 以后若新增正当跳到其他站点的路由，经过入口会返回 502，并体现在失败统计中。

## 其他上游请求

- 实例刷新时的 `/healthz` 检查（[scheduled.ts](../packages/server-core/src/scheduled.ts)）使用 `redirect: 'manual'`，被重定向的实例按不健康处理。整站跳转的实例（迁移或失效的域名、登录网关）在刷新时就会被排除；Feed 路由上的处理规则覆盖两次刷新之间的变化，以及只在部分路径上跳转的情况。
- 缓存探测 `/api/route/status` 使用默认的 `follow`。它只把 200 当作命中，不带客户端请求头，结果只影响尝试顺序，实际转发按上面的规则判断。
