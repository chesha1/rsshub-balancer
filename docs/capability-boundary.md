# 项目能力边界

本文档用来明确 `rsshub-balancer` 的定位、已经覆盖的能力，以及后续不再继续扩展的范围。

## 项目定位

`rsshub-balancer` 是一个 RSSHub 轻量 HTTP L7 路由器。它的目标是复用 RSSHub 实例已有缓存，减少重复抓取，并通过上游失败避让和源站故障接管维持入口可用性。

当前应用按职责分工：

| 应用 | 职责 |
| --- | --- |
| Origin | Node 常驻源站，日常承接 RSS 转发、健康检查、缓存状态和首页数据查询 |
| Edge | Cloudflare Worker，托管首页与静态资源、接收 Origin 指标，故障时承接同一套业务路由 |
| Watchdog | 独立 Cron Worker，探测入口可用性，通过增删 catch-all Route 控制接管与恢复 |
| Web | Vue 首页，展示当前候选上游和最近 24 小时请求分布，由 Edge 托管 |

Origin 和 Edge 共用 `server-core` 中的 Hono 路由、上游选择、实例刷新、存储规则和指标协议，分别提供 Redis 与指标的平台实现。项目维持这些职责，不扩展成通用负载均衡器或大型基础设施控制面。

## 当前项目能做什么

### RSSHub HTTP 请求转发

普通 Feed 路由仅接受 `GET` / `HEAD`，通过 `hono/proxy` 转发到 RSSHub 上游，其他方法返回 405。上游的 200–399 响应可以直接转发，重定向交给客户端处理。首页、健康检查、缓存状态和内部数据接口有各自的处理路径；具体兼容范围见 [README](../README.md#rsshub-接口兼容范围)。

`/_assets` 目录和根目录静态文件（根目录下扩展名为图片、图标、样式、脚本或字体的单段路径，如 `/favicon.ico`、`/apple-touch-icon.png`）属于本站资源，共享路由在进入代理前直接返回 404，不转发给上游，也不计入统计。归属只由请求路径决定，不看请求头，也不维护 RSSHub 路由清单；范围之外的未知路径继续尽力代理，项目不承诺识别任意无效 URL。

### 缓存感知路由

对于目标路由，项目并行探测候选上游的 `/api/route/status`，每个实例最多等待 1 秒。收齐时限内的结果后，从命中缓存的实例中等概率随机选择首个请求目标；未命中或首个请求失败时，按随机排列的候选顺序继续尝试。探测超时不会排除该实例参与后续转发。

这里复用的是上游 RSSHub 的缓存；应用没有自建 Feed 正文缓存。

### 简单失败兜底

当某个上游请求失败时，项目按 `pathname + upstream` 写入有效期为 6 小时的失败标记，不含查询参数。后续同路径请求在有效期内跳过该上游；全部候选被标记或本次尝试全部失败时返回 502。

失败标记是辅助状态：读取失败时按未标记处理，写入失败时记录日志并继续选路，不提供强一致保证。

### 上游实例刷新

Origin 在启动时和每小时刷新实例，Edge 通过每小时 Cron 独立刷新。两端都拉取远程 RSSHub 实例列表，合并自维护实例并排除自身，再检查各实例的 `/healthz`；只有返回 2xx 且正文为 `ok` 才进入新列表。没有健康实例或刷新失败时保留旧列表。

两端使用 Redis / Valkey 保存各自命名空间中的实例列表和失败标记，并在各自进程或 isolate 内缓存实例列表。Origin 复用 Redis 连接，Edge 每条命令独立建连并关闭；切换入口不交换状态。详见 [Redis](redis.md)。

### 源站故障接管

Watchdog 每 3 分钟检查一轮：正常时探测主域名，接管时探测固定 Origin 入口。探测同时要求健康接口与配置的业务 Feed 通过；同一轮内间隔 10 秒连续确认两次后，最多增删一次接管 Route，并读回确认。

这是针对当前 Origin / Edge 部署的有限故障切换，不是任意上游的实时调度系统。运行与维护约定见 [README](../README.md#运行与接管)。

### 基础观测

项目使用结构化日志和请求 ID 关联选路、缓存探测与上游尝试；Origin 批量上传指标至 Edge，Edge 与 Origin 的请求结果统一写入 Workers Analytics Engine。

首页展示实际进入 RSS 代理的请求分布，维度为来源国家/地区、请求一级路径与最终成功上游或请求失败。本站资源不进入代理，平台缓存直接返回的请求也不计入，指标允许丢失，也不作为故障切换依据。字段和统计边界见 [Metrics 查询](metrics.md)。

## 当前项目不做什么

### 不做通用软件负载均衡器

本项目不支持，也不计划支持：

- L4 TCP / UDP 负载均衡
- 数据库代理
- Redis / PostgreSQL / MySQL 代理
- 通用反向代理网关
- 大规模 WebSocket 网关
- 面向任意上游协议的长连接与连接池管理
- 连接级调度和 backpressure

这些能力超出 RSSHub HTTP 入口的职责范围。

### 不做复杂调度系统

本项目不计划实现：

- 动态权重调整
- 一致性哈希
- 会话粘滞
- 多租户策略路由
- 复杂灰度系统
- 通用主动健康检查控制面
- 完整熔断和限流框架
- 基于全局实时状态的调度

当前的目标只是“尽量把请求转到已有缓存的 RSSHub 实例，并在失败时尝试下一个上游”。

### 不扩展通用基础设施控制面

现有 Node 常驻进程、Redis 连接复用、实例刷新和独立 Watchdog 都服务于当前入口。项目不在此基础上继续扩展分布式任务调度、强一致全局状态、自建 tracing 平台或复杂发布编排。

Origin 保持单实例 Docker Compose 发布，接受短暂断流；当前取舍见 [Node 源站发布策略](origin-release-strategy.md)。

## 维护方向

后续默认按“功能冻结”维护。

可以接受的改动：

- 修复现有转发、接管、状态存储、日志或指标中的明确问题
- 补充必要文档
- 处理 Node、Cloudflare、Wrangler 和依赖版本变化导致的兼容问题
- 降低现有功能的运行成本或故障噪音
- 小范围清理代码，让现有行为更容易理解和维护

不再接受的方向：

- 把项目改造成通用 LB
- 加入大型控制面
- 继续增加复杂 Cloudflare 组件依赖
- 引入需要强一致状态的新功能
- 扩展面向任意协议的连接管理或通用后台调度系统
- 为了功能扩展而显著增加排障难度
