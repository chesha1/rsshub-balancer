# 项目能力边界

本文档用来明确 `rsshub-balancer` 的定位、已经覆盖的能力，以及后续不再继续扩展的范围。

## 结论

`rsshub-balancer` 是一个部署在 Cloudflare Workers 上的 RSSHub 轻量 HTTP L7 路由器。它的目标是复用 RSSHub 实例已有缓存，减少重复抓取，并在简单故障场景下做有限兜底。

这个项目不会继续发展成完整的软件负载均衡器，也不会继续在 Cloudflare Workers 上堆更多复杂基础设施能力。后续维护重点仅限于：

- 修复明确 bug
- 处理安全和依赖更新
- 保持现有部署兼容
- 改善文档、日志和必要的排障信息
- 做低风险、低复杂度的小幅维护

不再规划新增大型功能。原因很简单：在 Cloudflare Workers 这类 Serverless 环境里，很多传统后端和负载均衡器里自然成立的事情都会变得麻烦，包括常驻进程、连接池、强一致状态、深度可观测性、复杂健康检查和长期控制循环。

## 当前项目能做什么

### RSSHub HTTP 请求转发

项目接收外部 HTTP 请求，并把请求转发到可用的 RSSHub 上游实例。它工作在 HTTP L7 层，只处理 Workers `fetch` 模型能自然表达的请求。

### 缓存感知路由

对于目标路由，项目会探测 RSSHub 上游的 `/api/route/status` 接口。如果某个上游已经有对应缓存，就优先把请求转发给这个上游。

这不是完整的负载调度算法，而是围绕 RSSHub 缓存复用做的一层轻量选择。

### 简单失败兜底

当某个上游请求失败时，项目会在状态存储中写入短 TTL 的失败标记，并在后续请求中优先尝试未标记失败的上游。

这个失败标记是辅助性的，不提供强一致保证，也不等价于传统负载均衡器的主动健康检查、熔断系统或实时权重调整。

### 两级请求合并

对于并发的 `GET` / `HEAD` 请求，项目会做两级请求合并：

- Worker isolate 内使用本地 `Map` 合并同路径同方法请求
- 跨 isolate 使用 Durable Object 合并同路径同方法请求

这个能力用于减少同一时间对上游的重复请求。它依赖当前请求生命周期，不是通用缓存系统，也不是长期队列或任务调度系统。

### 上游实例刷新

项目通过定时任务拉取远程 RSSHub 实例列表，并用 `/healthz` 做简单可用性筛选。筛选结果写入状态存储，作为后续请求的上游列表。

这只是定时刷新，不是实时服务发现系统。

### 基础观测

项目已经记录结构化日志、请求 ID 和 Workers Analytics Engine 指标，用于观察请求转发、请求合并和上游访问结果。

这些观测能力服务于当前项目排障，不会扩展成完整 metrics 平台、tracing 平台或底层性能分析系统。

## 当前项目不做什么

### 不做通用软件负载均衡器

本项目不支持，也不计划支持：

- L4 TCP / UDP 负载均衡
- 数据库代理
- Redis / PostgreSQL / MySQL 代理
- 通用反向代理网关
- 大规模 WebSocket 网关
- 长连接连接池管理
- 连接级调度和 backpressure

这些能力需要长期连接、稳定进程、底层网络控制和更完整的数据平面，不适合继续堆在 Workers 里。

### 不做复杂调度系统

本项目不计划实现：

- 动态权重调整
- 一致性哈希
- 会话粘滞
- 多租户策略路由
- 复杂灰度系统
- 通用主动健康检查控制面
- 完整熔断和限流框架
- 基于全局实时状态的调度

当前的目标只是“尽量把请求转到已有缓存的 RSSHub 实例，并在失败时尝试下一个上游”。

云下迁移另行设计了固定业务域名的探活与 Route 接管：独立探活 Worker 自动切到云上，两个手动 Actions 负责接管和恢复，均直接调用 Cloudflare Route API，不引入 DO 或共同控制入口；该机制尚未实施，详见 [迁移与故障接管操作手册](worker-migration/migration-failover-runbook.md)。它只管理一个域名的云上/云下开关，不扩展上游调度策略。

### 不把 Cloudflare KV 当数据库

KV 只适合低频配置和辅助状态。项目历史上已经遇到 KV 写入成本、写入限制和最终一致性带来的不适感，因此不会把更多高频写入、强一致状态或复杂查询继续压到 KV 上。

当前状态存储可以切换到 Redis / Valkey，但这也是为了降低现有路径的摩擦，不代表项目要继续扩展成复杂状态系统。

### 不追求深度平台能力

Cloudflare Workers 适合做边缘请求处理，但不适合作为完整基础设施控制面。项目不会追求：

- 进程级 profiling
- 自建 tracing pipeline
- 精细网络栈排查
- 长期内存状态管理
- 自定义后台控制循环
- 平台外的复杂连接管理

这些能力如果真的需要，应迁移到常驻后端、专用负载均衡器或托管负载均衡产品中。

## 维护方向

后续默认按“功能冻结”维护。

可以接受的改动：

- 修复现有转发、合并、状态存储、日志或指标中的明确问题
- 补充必要文档
- 处理 Cloudflare、Wrangler、依赖版本变化导致的兼容问题
- 降低现有功能的运行成本或故障噪音
- 小范围清理代码，让现有行为更容易理解和维护

不再接受的方向：

- 把项目改造成通用 LB
- 加入大型控制面
- 继续增加复杂 Cloudflare 组件依赖
- 引入需要强一致状态的新功能
- 引入长期连接、连接池或后台守护进程假设
- 为了功能扩展而显著增加排障难度

如果未来确实需要完整负载均衡能力，更合理的方向是使用 Nginx、HAProxy、Envoy、Caddy、Traefik、云厂商 Load Balancer 或 Cloudflare Load Balancing，而不是继续在 Workers 里手写。

## 一句话边界

这个项目只做 RSSHub 场景下的轻量 HTTP L7 路由、缓存感知转发、简单失败兜底和请求合并；它不会继续演进成完整负载均衡器。
