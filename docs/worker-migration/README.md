# 云上云下迁移

本目录记录 `rsshub-balancer` 的云下迁移与云上故障接管方案，目前仍处于设计阶段，尚未实现或部署。

## 分析与审查范围

本目录的分析与审查以现有行为为基线，仅讨论本次从云上 Workers 迁移到云下 Node/Hono 所引入的问题、行为退化，以及保持既有行为和云上接管能力所必需的适配。

云上或云下原本就存在、并非本次迁移引入的缺陷，允许随现有逻辑一并保留，不作为本次迁移的设计缺口、实施要求或验收阻塞项。需要记录的既有问题放入 [TODO](../todo.md) 另行处理，不借迁移扩大为通用代码或架构整改。

提出迁移问题时，应说明迁移前后的具体变化及其因果关系。仅发现旧实现不够完善，或认为某项旧缺陷在另一运行时更值得关注，不自动将其纳入本次迁移范围。

## 迁移初心

这次迁移的直接原因是：Cloudflare Workers Paid plan 套餐内包含的 CPU Time 额度也已经接近用完。继续让主要 RSS 流量长期在 Worker 中执行，会增加超额使用带来的费用。

既然已经有一台服务器，就优先让它承接日常 RSS 流量，利用已有服务器资源，减少 Worker 的执行量和 CPU Time 消耗，降低运行费用。

同时，为了保障服务可用性（SLA），保留云上 Worker 的完整接管能力：云下服务器发生故障时，由 Worker 接手流量；云下恢复并验证通过后，再将流量切回。迁移的目标是兼顾日常成本与故障时的服务连续性。

## 目标运行方式

- **正常运行**：主要 RSS 流量由云下 Node/Hono 承接，边缘缓存命中的请求直接返回；首页页面、静态资源和桑基图内部接口继续留在云上 Worker，首页当前上游列表通过共享 `/api/upstreams` 从 Node 获取。
- **云下故障**：切换路由，让云上业务 Worker 接管 RSS 流量和当前上游列表查询，减少云下故障对服务的影响。
- **云下恢复**：确认云下服务健康并完成验证后，手动切回云下，恢复以服务器承接日常流量的状态。

首次迁移先完成两侧应用准备和手动切换，之后再接入自动探活接管与手动切换 Actions。具体步骤和接管时效以操作手册为准。
